# STV-M0-17: accounting journal ownership proposal

**Status: proposal for David/Cos review; not accepted.** Evidence reviewed at requested source `6d635f5` and current checkout `ddfcea67e34892dd0ddd861947bb740204d7855a`. This proposes one file-ownership protocol for #484. It does not approve an implementation, dependency, platform durability claim, or #483 incident lifetime. #485 remains responsible for drain/replay acknowledgements.

## Proposal

Keep each journal recovery domain local and private to one replica/installation. Steve remains multi-replica: each replica uses its own private local root, so replicas may share the same external configuration values while their journal stems resolve to separate local storage. The configured `queues.accounting_journal` stem is stable across process generations for that replica. Under it, persist `<stem>.owner-id`, `<stem>.incident.json`, a never-replaced `<stem>.coordination.lock`, and per-generation `<generation-uuid>.jsonl` plus `<generation-uuid>.state` files under `<stem>.owners/<installation-id>/`. Create/open the coordination file first, acquire its OS lock, then read/initialize the owner ID or incident record. On a genuinely empty first install, initialize the owner ID and `clear` record durably while holding that lock, before readiness; if either cannot be written and synced, fail startup visibly. If state is missing beside prior generation artifacts or a legacy journal, classify it as `unreconciled`, not first install. Each replica has independent incident state; no cluster-wide cutoff is implied. Shared-root or cross-host orphan discovery/recovery remains unresolved and unqualified.

Each process generation creates its journal privately, acquires the exclusive OS lock before canonical publication, then under the coordination lock publishes `<stem>.owners/<installation-id>/<generation-uuid>.jsonl` and a durably synced `active` state before readiness; it appends only after publication. Scanners inspect canonical files only and use nonblocking lock attempts. On orderly drain, #485's completion protocol may durably change that generation to `clean` before releasing its lock. Missing, corrupt, or non-clean generation state after its lock becomes available is `unknown`, even if its journal is empty: critical work may have died in a volatile queue. An OS lock held on a generation file protects it from concurrent writer/replay, but says nothing by itself about incident state or clean completion.

Persist the #483 incident state in one replica-scoped record under the same local root. Every shared read or read/modify/write snapshot takes the coordination lock and rereads the current monotonic revision, incident state, and generation/closure evidence; updates conditionally publish revision+1. A clear or acknowledged write based on a stale revision is rejected and can never overwrite a newer failure. A process latches a locally observed failure immediately, then atomically publishes `blocked` before releasing the coordination lock. A background reconciler polls complete incident and generation evidence every 50 ms and keeps one in-memory snapshot. Stamp the snapshot with the poll's **start** monotonic time, not its end, and set expiry to poll-start+100 ms. Readiness and inference admission consult only this in-memory snapshot, never the filesystem hot path; an incomplete or expired snapshot fails closed. After a successful blocked publication, a scheduled process observes it within the 100 ms freshness bound plus scheduling delay. A healthy active predecessor is not itself `unknown`; a replacement may become ready while it remains active when a complete, fresh snapshot says clear and all startup evidence is sound. If a process is unscheduled beyond the bound, no wall-clock observation promise applies; its first subsequent admission check sees the expired snapshot and rejects before accepting work.

If complete incident/generation evidence cannot be read or is malformed, the process latches `unreconciled`, becomes unready, and rejects inference with the proposed #483 `503 accounting_incident`; readiness is `503`, liveness/status remain available, and details use unknown/null values where evidence is unavailable. If a process holds the coordination lock but cannot commit `unreconciled` or a new `blocked` record, it stays locally blocked and retains that lock as an explicit fail-closed signal while alive; peers that time out acquiring it within 100 ms fail closed. If the detecting process cannot acquire the coordination lock, it cannot retain it: it blocks locally and retries. In that case, no peer-propagation bound is claimed unless the incident record is successfully published or peers independently observe stale/unreadable evidence. If the process exits before durable incident evidence exists, its `active` generation plus released generation lock is unclean-exit evidence; a scanner may mark the replica `unreconciled`, not clear, before reopening admission. If a peer itself observes unreadable evidence but cannot acquire the coordination lock, it blocks locally and retries; it does not claim to have published shared state. These rules bound observation only after successful publication or independently observed evidence failure on a qualified local filesystem.

The incident file is the authoritative cross-generation state. Writes use private temp file, file sync, atomic replacement, and containing-directory sync under the coordination lock. Readiness requires both the generation journal and `active` state to be synced while the coordination lock is held; partial startup remains unready and unknown. A busy journal lock means writer or replayer ownership, so scanners use a nonblocking attempt and never wait for it while holding the coordination lock. Lock timeout, read/write/sync failure, or unsupported atomic replacement is visible and fail-closed. A disposition/closure record must atomically bind the incident revision to the exact generation IDs and monotonic generation-state revisions it covers. Scans do not relatch the same acknowledged, unchanged evidence. A new generation failure or changed uncovered evidence that may represent loss creates a newer blocking revision; successful #485 reconciliation may advance using its newest revision/evidence. Before clear/ack, reread current incident revision and all closure evidence under the coordination lock; stale clear/ack loses to newer blocked state, and prior disposition remains in audit history. Replay failures retain their source. Successful replay may retire a closed file only after the acknowledgement and retirement ordering accepted by #485; never truncate a live journal file. Startup plus bounded post-start scanning discovers unclean/orphan generations. #485 owns generation completion/replay acknowledgement; #86 owns retry/exhaustion. #483 owns state names/admission ordering; its sticky-restart/operator-disposition policy remains pending. This record and revision protocol remove circular incident propagation without implying that a journal lock communicates incident state.

## Replacement and failure sequence

Order a same-replica rolling replacement as follows: (1) read the persisted installation ID and current #483 incident revision; (2) privately create and exclusively lock the new generation file, then acquire the coordination lock to publish it and durably write its `active` state; (3) take a complete evidence snapshot and mark ready only if it is fresh and admission is allowed, without waiting for a healthy old generation to exit; (4) mark the old process draining; (5) #485's clean-completion state must be durable before old generation lock release; (6) when an `active` generation lock becomes available, a scanner takes only a nonblocking generation lock attempt and checks its exact state revision. If that evidence is not already covered by the current incident disposition, it updates the current incident revision to `unreconciled` before admission resumes. Acknowledgement coverage names generation IDs and exact state revisions, so the same accepted, unchanged unclean generation does not relatch forever; a new generation failure remains a new blocking revision. Poll evidence every 50 ms from poll start, leaving 50 ms within the 100 ms freshness window for a complete read. New admission on transient lock/read errors fails closed; it may resume only after a later complete, fresh read and #483's accepted recovery transition. No wall-clock promise applies while a process is unscheduled.

| Event | Old owner | New owner | Journal rule / readiness consequence |
|---|---|---|---|
| Normal overlap | Holds a lock on its generation file and may append. | Uses the same local installation ID but a different generation file; scans eligible older files and polls shared incident state. | Busy means writer or replayer owns that file, not that the installation is incident-free. New may become ready while old remains active if shared incident and generation evidence allow it; old exit is not a readiness prerequisite. |
| New ready, old drains | Stops new admission under lifecycle rules; #485 defines how queued events and writer closure are acknowledged. | Continues using its own file. | Neither process writes or replays the other's live file. |
| Old exits cleanly | Closes writer and releases lock after its drain sequence. | May acquire the old file lock for replay, or a later process may do so. | Exact drain/replay completion and retirement order belong to #485. |
| Old crashes or is killed at any overlap point | OS releases its process lock; its file and missing clean-completion evidence remain. | A fresh snapshot uses a nonblocking lock attempt. If evidence is not covered by current disposition, it attempts to publish `unreconciled`. | Empty journal is still unknown because work may have been only in a volatile queue. If publication fails while holding coordination lock, keep local inference blocked and retain it; if lock acquisition itself fails, block locally and retry, with no peer cutoff claim until publication or observed evidence failure. |
| Two replacements scan one orphan | N/A | Only one can acquire its exclusive lock. | The loser skips the busy file; it does not read, truncate, or retire it. |
| Journal root cannot provide required lock semantics | May remain serving only if its already-established ownership is still valid. | Cannot safely decide live versus orphan ownership. | Fail the new process's storage/startup check visibly; do not silently share or truncate a file. Exact degraded/readiness behavior is for accepted incident policy and implementation. |

## Orphans, migration, and platform boundary

The persisted installation ID groups process generations for one replica across restart; generation filenames are the discovery hint. The internal incident ledger carries a monotonic revision and exact disposition coverage `(generation_id, generation_state_revision)` alongside the #483 incident object and audit reference. A per-generation durable clean-completion record, specified and acknowledged under #485, distinguishes orderly closure from an unclean exit. Missing, partial, or unqualified completion evidence means `unknown`, not clear; an empty journal cannot prove the bounded volatile queue was empty at crash time. Before any process serves, the first install durably initializes a clear incident record and its active generation record. On later starts, missing/corrupt incident evidence beside existing generation artifacts is unreconciled; never recreate it as clear. A 50 ms post-start scan with a 100 ms freshness deadline handles an old generation that exits after replacement readiness. This contract fixes the scan/freshness cadence; DB retry budget belongs to #86, forced-exit completion evidence to #485, and incident recovery transitions to #483. The proposed sticky-unknown-across-restart treatment aligns with #483's recommendation but is not approved; operator disposition remains a pending #483 acceptance question.

The staging-to-canonical rename must preserve the already-acquired lock and exclude scanners on Linux, macOS, and Windows. This behavior is not established by current source. If a supported platform/filesystem cannot prove lock retention over publication and safe lock/recovery semantics, reject that storage topology visibly; do not publish first and lock afterward. Pre-publication staging files are never replay candidates. If found after a crash, retain and classify them as incomplete/unknown until #485 defines safe cleanup evidence.

The existing flat `<stem>` file is not covered by the new ownership protocol and cannot be safely replayed or migrated while a pre-protocol binary may still append to it. The first adoption therefore needs an explicit legacy transition: stop all pre-protocol writers, preserve and inspect the flat file, then migrate/replay it under a single-owner procedure before normal rolling overlap begins. Do not auto-truncate, rename, or ignore a non-empty legacy file. If it exists on first startup and no accepted offline migration evidence is present, initialize `unreconciled` and fail readiness; do not create `clear`. Whether this one-time maintenance boundary is acceptable is an acceptance decision; source has no marker that can prove a legacy writer is gone.

The product remains multi-replica: each replica uses a distinct private local root, and healthy process overlap is supported within each replica's root using the same configuration values. This proposal does not qualify shared-root replicas, network filesystems, or cross-host orphan recovery if a replica moves to another host. Implementation qualification must prove local lock exclusion, lock retention across staging rename, append visibility, file and directory sync for generation/incident records and retirement, and lock release after process death on each supported local OS/filesystem. It must also prove snapshot expiry, the 50 ms poll and 100 ms freshness/lock timeout, and fail-visible behavior. Current source and PR #488's proposal do not establish these guarantees. Existing dependencies include no journal lock abstraction; use platform APIs or consider a dependency only after the Dependency Advisor workflow and platform qualification. No dependency is approved here.

## Acceptance examples and limits

- **Accept:** old and new processes for one replica use the same external config and its private local journal root, share the persisted installation ID, and own different generation UUID files. New is ready while the old file remains locked and unchanged if complete, fresh incident/generation evidence is clear.
- **Accept:** multiple replicas continue serving with the same external config when each has a distinct private local journal root; this contract makes no cross-root recovery claim.
- **Accept:** two new processes discover one unlocked orphan. Exactly one can own/replay it; the other leaves it alone.
- **Accept:** owner crashes mid-append or DB replay. The file remains available for recovery; no replay code truncates a live file. Torn-tail interpretation remains #85's decision.
- **Reject:** a fixed `<stem>.run` marker prevents the replacement from becoming ready while a healthy old process runs.
- **Reject:** PID/timestamp guesswork authorizes replay, a busy file blocks replacement readiness, or replay success is inferred from a channel send or DB `ON CONFLICT DO NOTHING`.
- **Unqualified/out of scope:** power loss during append, DB commit, or file retirement; shared-root/multi-host recovery; moving a replica to a host that cannot see its old private root; legacy mixed-version overlap. These require explicit qualification or acceptance boundaries before implementation.
