# STV-M2-14D (#613): native TLS server integration proposal

**Status: proposal only.** This selects a candidate implementation path for the accepted [listener boundary](stv-m2-14a-listener-tls.md) and [management-auth boundary](stv-m2-14b-management-auth.md). It changes no runtime behavior and does not make remote inference or management safe. David/Cos must accept this exact revision before the implementation leaves below are dispatched.

## Current seam and recommendation

At main `c3ccaebb5e6fc57bb754058feb220a837ca5da3f`, `src/server.rs::run` binds two Tokio TCP listeners, marks readiness, and passes each to `axum::serve` with graceful shutdown. `src/net.rs::bind_listener` preserves IPv6 wildcard dual-stack behavior. `ServerConfig` has no TLS fields. `tokio-rustls = 0.26.5` is a development dependency for the upstream TLS fixture, not a production server dependency.

Recommend `axum-server = 0.8.0` with [`tls-rustls-no-provider`](https://docs.rs/crate/axum-server/0.8.0/features), plus a direct `rustls = 0.23.45` dependency with `ring` and `tls12` features, for the native TLS serving branch. Steve's resolved Rustls graph already enables both AWS-LC and Ring, so [RustlsConfig::from_pem](https://docs.rs/axum-server/0.8.0/axum_server/tls_rustls/struct.RustlsConfig.html) cannot safely rely on automatic provider selection. At `main` entry, before configuration load or command dispatch, [install](https://docs.rs/rustls/0.23.45/rustls/crypto/struct.CryptoProvider.html#method.install_default) `rustls::crypto::ring::default_provider()` as the process default; if installation fails, return a safe startup error. This intentionally selects Ring for every command's in-process Rustls users, including `Doctor` database/object clients. Prove the exact resolved feature graph and real-daemon `Serve` and `Doctor` startup with both provider features enabled. Dependency Advisor Rust `standard` recommended `axum-server` 0.8.0 and `rustls` 0.23.45 with a 336-hour minimum release age on 2026-09-28; refresh both reports before changing `Cargo.toml`.

`RustlsConfig` parses PEM certificate/key bytes, [from_tcp_rustls](https://docs.rs/axum-server/0.8.0/axum_server/fn.from_tcp_rustls.html) accepts an already-bound standard TCP listener, and its [Handle](https://docs.rs/axum-server/latest/axum_server/struct.Handle.html) supports graceful shutdown. Keep the existing `bind_listener` behavior by converting its Tokio listener with `into_std()` only after the accepted pre-bind checks succeed. No new custom HTTP or TLS accept loop is proposed.

The alternative is a custom implementation of Axum's public [Listener](https://docs.rs/axum/0.8.9/axum/serve/trait.Listener.html) over `tokio-rustls`. A sequential handshake inside `accept` can let one stalled peer block later accepts; concurrent handshakes require a queue, task ownership, timeouts, and shutdown handling. That code is larger and security-sensitive. Avoid it unless the recommended server fails the exact lifecycle or platform checks below.

## Startup and transport contract

1. Parse both numeric `SocketAddr` values and classify loopback versus remote using the accepted #576 rule. Defaults become `127.0.0.1:11435` and `127.0.0.1:8790`; existing environment override precedence remains. A malformed value fails before either bind.
2. Add a strict `[server.security]` table with `tls_mode = "disabled" | "native_tls"` and paired `tls_cert_file` / `tls_key_file` fields. Unknown keys, an unknown mode, certificate paths in disabled mode, or a missing path in native mode fail before either bind. Disabled mode is allowed only for two loopback listeners. If either address is remote, both listeners use TLS.
3. With the selected Rustls provider installed at process entry, before binding open both files once, verify regular-file metadata and the key access policy on those handles, then read those same handles and pass the bytes to `RustlsConfig::from_pem`. This avoids a metadata-check/path-reopen race. Reject malformed PEM or a mismatched certificate/key pair, and prove that both listeners negotiate TLS 1.2 and TLS 1.3 while rejecting earlier versions. Load one immutable configuration for both listeners. Report only safe configuration-key/path context; never log PEM bytes or secret-file contents. No plaintext retry occurs after TLS setup or handshake failure.
4. Native TLS may first be exercised on loopback. Remote inference remains rejected until #502 caller authentication is accepted and implemented; remote management remains rejected until #109 management authentication is implemented. Request headers such as `Forwarded` and `X-Forwarded-Proto` do not satisfy either gate or establish encrypted transport.
5. Preserve the existing two-listener readiness point and `Lifecycle` in-flight/drain behavior. The TLS branch uses one server handle per listener; shutdown must stop accepting on both and enforce one shared absolute drain deadline. A stalled handshake, idle keep-alive connection, or active stream cannot keep the process alive beyond the configured bound. The HTTP loopback branch continues to use `axum::serve`.

### Key permissions and platform limit

The accepted #576 rule rejects a key readable by unrelated identities or an access policy Steve cannot verify. A Unix mode-bit check alone is insufficient evidence for [macOS ACLs](https://developer.apple.com/library/archive/documentation/Security/Conceptual/AuthenticationAndAuthorizationGuide/Permissions/Permissions.html); Windows ACLs need their own verifier. On Linux, propose comparing open-file owner/mode with the process effective UID, rejecting group/other access and any POSIX ACL that the implementation cannot fully verify; access-check errors fail closed. [rustix 1.1.4](https://docs.rs/rustix/1.1.4/rustix/process/fn.geteuid.html) provides a safe effective-UID call and [open-file xattr inspection](https://docs.rs/rustix/1.1.4/rustix/fs/fn.fgetxattr.html). Dependency Advisor Rust `standard` recommended 1.1.4 with a 336-hour minimum release age on 2026-09-28; refresh before adding it as a direct Linux dependency. Prove the owner/access rule with restrictive and permissive fixtures on the supported Linux filesystem; reject unverified ACL/filesystem behavior. On macOS and Windows, `native_tls` must fail closed until a platform-specific ACL verifier and tests establish the same rule; loopback HTTP remains available. This is a proposed support limit for explicit review, not a claim that those platforms have passed TLS qualification. No permission relaxation is allowed to make a test pass.

Certificate rotation is restart-only, even though the candidate library offers reload APIs. Provision a new pair, validate the candidate before either bind, then retire the old pair after readiness and certificate checks. A supervisor/deployment owner must supply any replacement or rollback choreography; Steve's fixed-port process does not promise hitless overlap. Rollback uses the prior compatible binary and configuration together.
