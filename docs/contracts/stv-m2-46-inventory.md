## Current boundary and shared rules

`src/server.rs::management_router` currently exposes read-only status/version/provider-health endpoints and `POST /api/v1/system/drain`; it has no identity/key, credential, provider/account, grant/binding, pool, history-policy, or configuration write route. `drain` changes process lifecycle state but is not a persisted configuration change; include it as an operational management action when #109 supplies authenticated actor and denial seams. Its present handler only transitions lifecycle to draining and returns the phase. All other rows below are future behavior under their named owners.

`Config::load` reads a file or defaults, then applies environment overrides at process startup. The current `config_loaded` log reports the source path and selected non-secret settings; there is no file watcher, config mutation producer, or trustworthy operator identity. Static file/environment edits are **out of scope** for audit events. Reopen this boundary only when a management/controller write path supplies an authenticated actor and an authoritative managed-write source; a daemon restart or file path alone does not identify who changed it.

For a future managed operation, resolve authentication and authorization before validation or state mutation. Emit one operation result for success and each operation-level denial/failure: denied authorization, invalid input/reference conflict, failed mutation/commit, or committed success. Successful results are formed only after the owning store reports commit; failure results are formed when the operation reaches its final failure. Pre-route traffic that never resolves to a managed operation is not a configuration event. Authentication failures are emitted only where the auth boundary can report them without trusting supplied identity claims. Do not turn client labels, email, IP, headers, raw request data, or guessed principal ancestry into actor identity. Under the shared admin credential, Organisation/User/Client are `unknown` and Session/Turn/Request/Attempt are `not_applicable` unless independently trusted context supplies them.

For future managed operations using #106's shared `management.admin` bearer credential, propose `actor.kind=management_admin` and `actor.id=null`: it authenticates a role, not a person or #99 principal. Organisation/User/Client attribution is unknown. Session/Turn/Request/Attempt are not applicable to a management operation unless independently trusted context supplies them. Failed authentication uses `actor.kind=anonymous` and `actor.id=null`, with unknown identity and no supplied identity claims. Preserve additional spec §5 attribution only when an accepted contract independently provides it; the current source provides none. Target references come from the owning domain contract; this proposal assigns no IDs or field values. The registries below propose the action/target/error bindings for joint #513/#514 acceptance; exact envelope schema binding remains #513's owner. #123 writer and mutation/audit persistence coupling remain #515's decision; this proposal does not decide whether a state mutation may succeed when audit persistence fails. Spec §17's no-silent-loss rule remains applicable without deciding that coupling.

V1 event content is limited to the envelope fields, actor/attribution, registered action, outcome, one target object, and required nullable error code. No correlation reference is proposed. There is no metadata or arbitrary payload field in this proposal. Exclude credentials, client keys/verifiers, secret-store material, authorization data, endpoint auth values, prompts/responses, and arbitrary request/config payloads recursively. Never include before/after values. If classification is uncertain, omit it; if a required field cannot be formed safely, use the accepted envelope's fail-closed rule rather than serializing raw input.

The envelope outcome enum is exactly `success`, `denied`, or `failure`. `error_code` is required and nullable: it is null for `success`; `denied` uses `unauthenticated` or `forbidden`; `failure` uses one of `invalid_input`, `not_found`, `conflict`, `secret_unavailable`, `backend_unavailable`, `mutation_failed`, `internal_error`, or `unclassified_failure`. These finite lower_snake codes summarize a class only; status text, SQL/provider messages, and raw input are never included. Apply the envelope’s exact target null/omission rules.

## Normative fixture requirement

Before each implementation consumer is re-sized/dispatched, add a small redacted contract fixture for each row that emits events. For every applicable family, include a `success` result, one representative `failure` result, and a `denied` result; include an authentication-failure case only where the accepted auth boundary emits one. The identity/key and provider-credential fixtures must explicitly prove secret, verifier, token, and credential values are absent. Fixtures must assert `error_code=null` for success and the registered required error code for denied/failure outcomes. History/storage/observability fixtures must prove content and credential material are absent. Routing fixtures must cover profile and rule writes. All fixtures use symbolic types/placeholders in documentation, not invented observed IDs or runtime values, and are future-behavior examples, not test evidence. Static configuration has no event fixture because it is out of scope until a trusted runtime source exists.
