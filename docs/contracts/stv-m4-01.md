# STV-M4-01 proposal: fixed-point money representation

**Status:** Proposal only; David/Cos acceptance pending. No current money type or decimal arithmetic was found under `src`; Cargo has no decimal dependency. No runtime/schema change is made here.

Source: [spec §10](../specs/2026-09-26-steve-gateway.md#10-pricing-and-currencies), [M4 plan](../plans/2026-09-26-steve-mvp.md#m4--pricing-and-accounting), inspected against main `4472ca59896465fcf27b0d1df1d5218552d80efd`.

## Proposed representation and arithmetic

- Propose one arithmetic representation: signed `i64` ticks at scale `S=1,000,000,000` (9 decimal places) for currency amounts, unit prices, and FX rates. Decimal types can support more fractional places but require an additional implementation/dependency and backend conversion rules; scaled ticks use SQLite `INTEGER` / PostgreSQL `BIGINT` via SQLx `i64`. Use checked Rust `i128` intermediates only; do not persist decimal text for arithmetic, use binary float, SQLite `SUM`/`total()`, or assume a database `i128` type.
- Stored nonnegative amount/rate range is `0..=i64::MAX` ticks = `0..=9,223,372,036.854775807` major units; exclude `i64::MIN`. Provider unit prices and charges must be nonnegative (zero only when explicitly known free/zero); FX rate must be positive. Negative prices/rates/charges are rejected; separately typed refunds/credits are outside this decision.
- Parse source decimal text exactly, never through `f64`. Accept values representable at 9 places; extra fractional digits are allowed only when all discarded digits are zero, otherwise reject as unsupported precision. Preserve original source amount/currency/unit/version/provenance alongside normalized ticks. `None`/unknown is distinct from numeric zero.
- At JSON boundaries, encode the scaled coefficient as a base-10 integer string in an explicitly scaled field, never as a JSON number that a client may round through binary float. Field names and complete API envelopes remain #298.
- A computed zero from a known metered line remains metered, not free; retain inputs so its rounding is reproducible. Missing data cannot select a free/zero mode.
- FX rate is quote-major-units per one base-major-unit, in the same ticks. Source-to-USD uses USD/source; display conversion uses display-currency/USD. USD identity is exactly `1.000000000`. Missing/stale captured FX yields unknown canonical USD or local display respectively; never substitute a latest rate.
- Persist source price and canonical USD unit price at S precision with source unit, currency, price version/effective/retrieval dates and provenance. Normalize the USD quoted-price ticks as `round_half_even(price_ticks * usd_per_source_ticks / S)`, retaining the same source unit basis. This normalized USD unit price is a snapshot for comparison/display only; usage charges must not multiply a prematurely rounded USD unit price.
- Calculation inputs `quantity` and `unit_basis` are integers in the same accepted usage unit, with `0<=quantity<=u64::MAX` and `1<=unit_basis<=u64::MAX`; #166 must supply this exact ratio, including any fractional media-duration conversion. Capture these inputs for reproduction. Never pass a binary-float quantity.
- `round_half_even(n/d)` means nearest integer, with exact ties selecting the even integer. Keep quotient and remainder until this operation; integer truncation before rounding is forbidden. For nonnegative n and positive d, compare remainder with `d-remainder` to avoid overflowing a doubled remainder.
- After #166 resolves the price tier/unit and aggregates usage quantity for a charge dimension (no per-stream-chunk rounding), compute source line ticks as `round_half_even(price_ticks * quantity / unit_basis)`. Then compute canonical USD ticks directly from unrounded source inputs: `round_half_even(price_ticks * quantity * usd_per_source_ticks / (unit_basis * S))`. Use checked `i128` for every product/division; unsupported unit denominator, intermediate overflow, or final out-of-range result is explicit error/unknown, never truncation or saturation.
- Round only at the named persisted boundaries: normalized USD quoted price to S ticks; source charge line to S ticks; USD charge line directly from source price × aggregated quantity × captured FX to S ticks; display line once to the target currency's accepted minor-unit exponent. `#170` known quantity × immutable unit price returns known zero for quantity zero; absent/unknown input returns `Unknown`, not zero.
- Display conversion (`#237`) starts from known canonical USD and captured display FX, then rounds half-even once to the currency minor unit exponent `e` supplied by accepted currency metadata (`0<=e<=9`); absent/unsupported exponent is unknown. Let `k=S/10^e`. Compute `minor_units=round_half_even(usd_ticks * display_fx_ticks / (S * k))`, then `display_ticks=minor_units * k`, using checked `i128` intermediates and enforcing the stored `i64` range. Persist display ticks at the common S scale, quantized to the currency minor unit; do not first round the conversion to S ticks. Persist the display currency and FX snapshot used when configured. If FX is absent/stale per #165, display is unknown while USD remains. A currency change does not reprice historical rows; sum display rows only within one currency, otherwise report separately.
- Sum persisted source/USD/display ticks in application code using checked `i128`, in any row order; enforce `i64` range before persisting a total. On any checked-intermediate, aggregate, or storage overflow, return explicit overflow/unknown and do not write a partial total. Never coerce to `REAL` or use decimal-text SQL arithmetic.
- Example: source price EUR `1.25` per 1,000 units, quantity 300, USD/EUR `1.20`: source line = `375,000,000` ticks (€0.375); direct USD line = `450,000,000` ticks ($0.45). USD unit price is $1.50 per 1,000 but is not used to derive that line. At display FX AUD/USD `1.50`, $0.45 = A$0.675 → A$0.68 at 2 minor digits (half-even).
- Aggregation is order-independent: charge each resolved usage-dimension line once, then add its persisted integer ticks exactly; do not round token/chunk subtotals or round the summed USD total again. Historical charge rows retain source price/unit, usage quantity/unit basis, canonical USD, and exact source→USD FX value/time/source; display retains its distinct captured FX snapshot.

**Boundaries/open acceptance:** proposed scale/range/rounding and overflow rules need David/Cos approval. #165 selects FX source and freshness; #166 selects usage units/tier semantics; #196 captures charge FX; #170 owns dimension charge calculation; #237 converts known USD with captured FX; #238 owns display-currency preference. If any required input is absent/stale/unsupported, preserve source evidence and return unknown instead of fabricating a value. No provider catalog, FX source, tier policy or complete table/API layout is selected here.
