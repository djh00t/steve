## Proposed policy

| Situation | Proposed behavior |
|---|---|
| Export disabled by #545's configuration | Do not enqueue/export OTLP records. Continue local application logging and built-in management reporting. Intentional disablement adds zero to `telemetry_dropped`. |
| Queue full or closed | The producer uses the existing telemetry sender's nonblocking `try_send`; abandon that one event and increment `telemetry_dropped` once. Never wait for queue capacity. |
| Export accepted | A normal response without `partial_success` confirms acceptance of all request items. A partial-success response with zero rejected items also accepts all items (it may carry a warning); never retry any response with `partial_success` populated. |
| Export rejected or fails | Each request has one absolute service deadline: 2,250 milliseconds after the oldest included item is dequeued, capped by the shared shutdown deadline. Preparation, jitter, and all attempts count against it; batching cannot reset or extend it. Each of at most two attempts also has a 1-second sub-cap. Retry once only for a pre-send connection failure confirming no request bytes were sent, with random jitter in the closed interval 125–250 milliseconds, clipped to the remaining absolute budget. Partial success, any HTTP response failure, a timeout after send may have begun, or any ambiguous result is not retried. If time expires, abandon/count all unconfirmed input items once. The adapter must disable hidden SDK retries; the worker owns this single retry budget. No durable spill or replay. |
| Exporter offline | Continue best-effort exports within those bounds. The existing finite queue may fill; each abandoned event is counted as above. Inference forwarding and built-in management reporting do not depend on exporter health. |
| Shutdown | Use one hard deadline computed at the initial shutdown trigger: trigger time + configured `drain_timeout_seconds` (60 seconds by default). Continue best-effort export only until that shared deadline. At the deadline, stop export and abandon/count each pending or in-flight unconfirmed event once. Do not add time beyond the configured request-drain deadline. |

### Record and loss units

One queued normalized telemetry event is one OTLP item: one span, one log record, or one metric data point. An export request may batch `n` queued events, where `n` is known at send time and bounded by the configured queue capacity (8,192 by default). OTLP partial-success responses report rejected counts by signal (spans, log records, or metric data points), not rejected-item identities, and OTLP forbids retrying a request with `partial_success` populated. For valid partial success with rejected count `r` where `0 <= r <= n`, increment the event-loss counter by `r` once and never retry the request; no item identity is needed for this aggregate count. A zero rejected count means all `n` items are accepted (the response may carry a warning). If the rejected count is invalid or exceeds `n`, abandon/count all `n` items once. Do not invent per-record wire IDs. A normal success without `partial_success` confirms acceptance of all `n` items.

The loss-counter unit is one queued event that Steve abandons without confirmed acceptance, independent of send-attempt count. A timeout or shutdown may be ambiguous: the exporter may have accepted an event without Steve receiving confirmation. The counter means Steve stopped tracking/retrying that event; it does not claim the receiver definitely failed to ingest it. Queue refusal and shutdown abandonment count each affected queued event. For valid partial success, count rejected-item total `r`, not attempts or requests. A final request failure counts its `n` input events once; retries do not add counts. OTLP/HTTP recommends retry for 429, 502, 503, 504, and connection failures, and requires jitter between connection retries. This proposal deliberately retries only confirmed pre-send connection failures, not post-send HTTP response failures (including those status codes) or ambiguous outcomes, to bound work and avoid replay after uncertain acceptance. This narrows best-effort delivery and may lose events that another retry could deliver; it is a proposal for acceptance, not an OTLP requirement.

`telemetry_dropped` is cumulative for the process lifetime, starts at zero, and does not reset when the queue drains or the exporter reconnects. It increments once for each abandoned event and saturates at `u64::MAX` rather than wrapping, preserving monotonicity. The existing local queue snapshot exposes it while Steve is running; emit the final count through local structured logging before exit if shutdown abandons pending events. An unavailable exporter cannot be the only place that reports its own loss.

The 2.25-second value is an absolute **post-dequeue export service deadline** for one request, not maximum queue wait or event age. It starts when the oldest item in that request is dequeued and includes preparation/serialization, jitter, and both attempts; queue wait is separate. The earlier shared shutdown deadline always wins. Enforce the budget with cancellation/timeouts, but do not claim a hard real-time OS scheduling guarantee. The queue retains at most its configured capacity (8,192 by default), with no promise that pending records survive restart. No queue-age/TTL policy is introduced here.

## Observable examples

1. With export disabled, an inference request completes and local reporting remains available; no OTLP event is enqueued and loss count does not increase.
2. With a full or closed telemetry queue, one attempted event returns immediately and increments `telemetry_dropped` by exactly one; the inference request does not wait.
3. For a request with `n` items, a valid partial-success response with rejected count `r` is not retried and increments the counter by `r`; a zero-rejection warning response increments it zero times.
4. A confirmed pre-send connection failure receives at most one jittered retry within the original dequeue-based 2,250-millisecond deadline; preparation, batching and the retry do not reset it. An ambiguous post-send timeout does not retry. Each abandoned event increments the counter once, while forwarding and built-in reporting continue.
5. At shutdown, queue flushing stops at the original shared deadline; pending/unconfirmed events are counted once, the final count is logged locally, and exporter handling adds no time after that deadline.
