# Steve MVP Delivery Plan and Backlog

Date: 2026-09-26
Status: Approved scope baseline. The [reviewed work-package index](../backlog-index.md) is the execution breakdown; [testing policy](../testing.md) and [readiness rules](../work-packages.md) govern each package.

## MVP outcome

A developer or household can install Steve, create users, configure multiple provider accounts, point OpenAI/Anthropic-compatible clients at it, route traffic, and see exactly:

- who made each request;
- which client and chat/session it belonged to;
- which model/provider/account handled it;
- which upstream attempts failed or succeeded;
- how long each proxy and provider stage took;
- how many tokens/resources were consumed;
- what the request cost in canonical USD and optional local display currency;
- why a routing decision was made;
- where chat/history payloads were stored.

## Delivery order

### M0 — clean foundation

Deliver:

- Rust workspace and single `steve` binary;
- Tokio/Axum runtime;
- configuration loader;
- versioned management API skeleton;
- structured error model;
- SQLite and PostgreSQL connection/migration support;
- storage traits for relational and object storage;
- local filesystem object store;
- S3-compatible object-store implementation;
- tracing/logging foundation;
- bounded deferred-work queues with independent accounting/history/telemetry classes;
- lifecycle/readiness/draining state and in-flight request tracking;
- deterministic test upstream.

Acceptance:

- `steve serve` boots using SQLite or PostgreSQL.
- Health and management version endpoints work.
- Local object storage and S3-compatible storage pass the same contract tests.
- No dependency on Swift, Docker, or external telemetry to operate.
- Saturating a noncritical background queue does not block health/management request handling.
- A draining server becomes unready immediately while remaining live until its in-flight work completes.

### M1 — real proxy hot path

Deliver:

- OpenAI Responses ingress;
- OpenAI Chat Completions ingress;
- Anthropic Messages ingress;
- SSE streaming;
- cancellation/client disconnect handling;
- OpenAI-compatible upstream adapter;
- Anthropic upstream adapter;
- generic OpenAI-compatible provider;
- generic Anthropic-compatible provider;
- model listing and provider health.

Acceptance:

- OpenAI and Anthropic SDK-compatible clients can complete streaming requests through Steve.
- A stream is never silently replayed after output has begun.
- One logical request can record multiple upstream attempts.
- Accounting, history and telemetry side effects are queued/deferred and do not delay forwarding or streaming.

### M2 — identity and multi-account routing

Deliver:

- Organisation/User/Client schema;
- local API/client authentication;
- Provider and UpstreamAccount separation;
- account ownership and access bindings;
- AccountPools;
- multiple accounts per provider;
- dedicated, prefer-own, weighted, least-utilised, failover policies;
- user/session affinity;
- per-account health/rate-limit state.

Acceptance:

- Four household users can each have separate provider credentials.
- Shared accounts may be permitted for selected users/clients.
- Steve cannot route a user through an account they are not allowed to use.

### M3 — sessions and content history

Deliver:

- Steve session IDs;
- Session/Turn/Message schema;
- request-to-session linking;
- client/provider conversation identifier capture;
- exact/inferred/unknown association quality;
- local/S3 message and payload archival;
- ObjectRef indexing;
- configurable content logging and retention;
- session/history management API.

Acceptance:

- Every attributable request is linked to a user/client/session.
- A session can contain requests to multiple upstream providers.
- Content can be disabled while metadata/accounting remains intact.

### M4 — pricing and accounting

Deliver:

- PricingVersion model;
- source-currency preservation;
- canonical USD normalisation;
- FXRate provenance;
- local display currency setting;
- immutable historical price/FX snapshots;
- token/cache/context-tier pricing primitives;
- subscription/quota/free/unknown pricing modes;
- UsageCharge ledger;
- account/user/client/session/model/provider cost views.

Acceptance:

- Every billable successful or partially billable attempt has reproducible accounting.
- UI/API can display local currency while retaining USD and FX rate.
- Historical reports do not change when today's FX or provider list price changes.

### M5 — deep latency/error telemetry

Deliver:

- per-stage LatencySpan model;
- per-attempt connection/TTFB/TTFT/final-token timing;
- routing/auth/session/persistence timing;
- normalized ErrorEvent taxonomy;
- p50/p95 aggregates;
- short-window EWMAs;
- provider/account/model reliability summaries;
- structured logs;
- OpenTelemetry export.

Acceptance:

- A request timeline can explain user-observed latency.
- Provider/account latency and error history are queryable by routing.
- Built-in reporting works without Grafana.

### M6 — routing engine

Deliver:

- routing profiles and aliases;
- hard capability/access filters;
- fixed/rule-based routing;
- `RoutingEngine` abstraction;
- Switchyard adapter pinned behind that abstraction;
- provider/account candidate scoring;
- cost-aware selection;
- latency-aware selection;
- reliability/health-aware selection;
- quota-aware selection;
- deterministic failover;
- persisted RoutingDecision explanation.

Acceptance:

- `model=auto` produces an inspectable, reproducible decision.
- Router can prefer a faster/healthier provider using measured data.
- Removing/replacing Switchyard does not alter Steve's public contracts.

### M7 — full TUI

Deliver screens for:

- dashboard/system;
- providers;
- upstream accounts;
- users/clients;
- models/capabilities;
- pricing/FX;
- profiles/routes;
- sessions/history;
- usage/costs;
- latency;
- errors;
- object storage/retention;
- observability;
- diagnostics.

Acceptance:

- Everything the daemon can configure or report is accessible through the TUI.
- Remote TUI operation over the management API is supported.

### M8 — macOS Swift controller

Deliver:

- discover existing Steve deployment;
- signed, versioned native install/update/start/stop for the accepted managed channel;
- for native updates, a coordinator stages a candidate, verifies compatibility/readiness, routes new work, drains the old worker, and routes back automatically if the candidate fails before cutover completes;
- expand/contract compatibility for mixed-version operation while the old worker drains;
- Apple Container/Docker local setup;
- connect to remote Steve;
- optional localhost forwarding to remote;
- provider/account health and usage;
- daily/monthly cost;
- active routing profile;
- basic profile/route changes;
- deployment switching;
- open full management surface.

Acceptance:

- A macOS user with no Steve installation can select native, container, or remote during onboarding.
- Normal day-to-day profile/usage work requires no terminal.
- A managed native update uses a signed, versioned candidate and the coordinator sequence above; the serving worker remains available through readiness and cutover, failed pre-completion cutover routes back automatically, and migrations preserve old/new worker compatibility until old workers exit.

## Canonical end-to-end acceptance scenario

A home gateway runs Steve in an OCI container.

Users:
- David
- Alice
- Bob
- Charlie

Accounts:
- four personal ChatGPT/Codex-style accounts when supported;
- four personal Anthropic accounts when supported;
- one shared OpenAI API account;
- one OpenRouter account;
- one DeepSeek account.

David starts a coding client and authenticates to Steve. The client creates/continues a Steve session and requests an automatic model.

Steve:

1. resolves David, the client, and session;
2. evaluates allowed accounts;
3. selects an appropriate model/tier;
4. scores eligible provider accounts using configured policy plus cost, measured latency, reliability, quota, and affinity;
5. executes one or more attempts;
6. streams the successful response;
7. records every attempt and latency stage;
8. records token/resource usage and immutable USD accounting plus configured local-currency display values;
9. stores chat/raw payloads according to the configured retention policy;
10. emits optional OpenTelemetry signals;
11. exposes the request, session, cost, latency, errors, and routing explanation through the management API/TUI.

The Swift menu-bar app shows the active deployment, profile, provider/account health, usage, and spend and can switch the normal routing profile.

When this scenario works end-to-end, Steve has a useful MVP rather than merely a protocol proxy.
